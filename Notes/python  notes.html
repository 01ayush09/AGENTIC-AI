01
Object-Oriented Programming
class · __init__ · inheritance · ABC · dunder methods · @property · composition
class__init__inheritance @property@abstractmethod __repr__ / __str__ABC
Definition

OOP organises code into objects — bundles of data (attributes) and behaviour (methods). A class is the blueprint; an instance is the real object created from it.

Objective

Model complex systems as interacting objects rather than isolated functions. Enables reusability, encapsulation, and clear interfaces between components.

Reason to use

Agents are stateful systems. OOP lets you bundle memory, tools, and behaviour into one class — then specialise it through inheritance without rewriting core logic.

Key concepts

Encapsulation — hide internals with _private. Inheritance — share base behaviour. Polymorphism — same method, different behaviour. Abstraction — enforce interfaces via ABC.

from abc import ABC, abstractmethod
from typing import Optional

class BaseAgent(ABC):
    def __init__(self, model: str):
        self.model = model
        self.memory: list = []           # instance-level state

    @abstractmethod                      # subclass MUST implement this
    def run(self, task: str) -> str: ...

    def remember(self, msg: dict):
        self.memory.append(msg)

    @property                            # computed attribute, no ()  
    def turn_count(self) -> int:
        return len(self.memory)

    def __repr__(self) -> str:
        return f"<{type(self).__name__} model={self.model!r}>"

class ResearchAgent(BaseAgent):          # inherits everything above
    def run(self, task: str) -> str:
        self.remember({"role": "user", "content": task})
        return f"Researching: {task}"
How this connects to AI Agents

Every real agent framework (LangChain, LlamaIndex, custom) is OOP at its core. You'll define a BaseAgent with shared memory and tool logic, then subclass into specialised agents (research, coding, planning). Polymorphism lets you swap different LLM backends without changing orchestration code. ABC enforces that every agent subclass implements run() — preventing silent failures at deploy time.

Async / Await
asyncio · coroutines · event loop · gather · asyncio.Queue · async generators · aiohttp
async defawait asyncio.gatherasyncio.run aiohttp / httpx asyncio.Queue
Definition

Async lets a single thread handle many tasks concurrently by yielding control while waiting for I/O. async def defines a coroutine; await suspends it until a result arrives.

Why use it

LLM API calls take 1–20 s each. Without async, 5 sequential tool calls take 5×. With asyncio.gather all 5 fire in parallel — your agent appears instant to the user.

import asyncio, httpx

# ── coroutine: single LLM call ──────────────────────────────
async def call_llm(client: httpx.AsyncClient, prompt: str) -> str:
    resp = await client.post("https://api.anthropic.com/v1/messages",
                              json={"messages": [{"role":"user","content":prompt}]})
    return resp.json()["content"][0]["text"]

# ── fire all in parallel with gather ──────────────────────────
async def parallel_tools(prompts: list[str]) -> list[str]:
    async with httpx.AsyncClient() as client:
        tasks = [call_llm(client, p) for p in prompts]
        return await asyncio.gather(*tasks)     # all run simultaneously

asyncio.run(parallel_tools(["summarise", "translate", "classify"]))
Trap: never use time.sleep() or requests.get() inside async functions — they block the entire event loop. Use asyncio.sleep() and httpx.AsyncClient / aiohttp.
How this connects to AI Agents

Every production agent is fully async. When an agent invokes multiple tools in parallel (web search + database lookup + code execution), asyncio.gather runs them simultaneously. Streaming LLM responses use async generators to forward tokens to the user in real time. The FastAPI server exposing your agent is async. Without this, your agent will be 3–10× slower and unable to handle concurrent users.

Decorators
function wrappers · @wraps · @property · @classmethod · @staticmethod · @lru_cache · parameterised decorators
@wraps@lru_cache@property @classmethod@tool (LangChain)@retry
Definition

A decorator is a function that wraps another function, adding behaviour before/after without modifying the original. @decorator is syntactic sugar for fn = decorator(fn).

Why use it

Cross-cutting concerns (logging, retry, caching, timing) shouldn't pollute business logic. Decorators keep each concern separate and reusable across hundreds of functions.

import functools, asyncio, logging

# ── parameterised decorator: exponential-backoff retry ──────
def retry(attempts: int = 3, delay: float = 1.0):
    def decorator(func):
        @functools.wraps(func)          # keeps __name__, __doc__
        async def wrapper(*args, **kw):
            for i in range(attempts):
                try:
                    return await func(*args, **kw)
                except Exception as e:
                    if i == attempts - 1: raise
                    await asyncio.sleep(delay * 2**i)  # 1s, 2s, 4s…
        return wrapper
    return decorator

@retry(attempts=3, delay=0.5)
async def call_llm(prompt: str) -> str: ...

# ── caching decorator: skip duplicate embed API calls ────────
from functools import lru_cache

@lru_cache(maxsize=512)
def embed(text: str) -> list[float]:
    return embedding_model.encode(text)  # only called once per unique text
@property
class Agent:
    @property

          len(m["content"])

@classmethod vs @staticmethod
class Agent:
    @classmethod
    def from_config(cls, cfg):
        return cls(cfg["model"])  # factory

    @staticmethod
    def count_tokens(text):

How this connects to AI Agents

Agent frameworks register callable tools with a @tool decorator — it marks a function as LLM-invokable and auto-generates the JSON schema the model needs. Retry decorators silently handle Anthropic/OpenAI rate limits. @lru_cache prevents redundant embedding API calls in RAG pipelines. Logging decorators add full observability to every LLM call without touching business logic.

Type Hints
annotations · Union · Optional · Literal · TypedDict · Generic · Protocol · mypy
str | Nonelist[dict] TypedDictLiteral Generic[T]Protocolmypy
Definition

Type hints annotate variables and function signatures with expected types. Python doesn't enforce them at runtime, but mypy, IDEs, and Pydantic use them to catch shape mismatches before execution.

Why use them

Agent code passes deeply nested structures (tool schemas, LLM responses, config) through many layers. Hints make intent explicit, enable autocomplete, and prevent entire classes of runtime KeyError / AttributeError.

from typing import TypedDict, Literal, Optional, Protocol

# TypedDict — typed shape for dicts (no class overhead)
class Message(TypedDict):
    role: Literal["user", "assistant", "system"]  # only these 3 strings
    content: str

# Protocol — structural typing: any object with .run() qualifies
class Runnable(Protocol):
    def run(self, task: str) -> str: ...

# Generic — parameterised container
from typing import Generic, TypeVar
T = TypeVar("T")

class MemoryStore(Generic[T]):
    def __init__(self): self._items: list[T] = []
    def add(self, item: T): self._items.append(item)
    def get_all(self) -> list[T]: return self._items

msg_store: MemoryStore[Message] = MemoryStore()  # fully typed

How this connects to AI Agents

Pydantic — the backbone of FastAPI, LangChain tool schemas, and structured LLM output parsing — is entirely built on type hints. Every tool schema, agent config, and LLM response model you define will use TypedDict or Pydantic BaseModel. Literal restricts role fields to exactly "user"/"assistant". Protocol lets you write an orchestrator that works with any LLM backend without coupling to a concrete class — swap Anthropic for OpenAI with zero orchestration changes.

05
Dataclasses
@dataclass · field() · frozen · __post_init__ · Pydantic BaseModel
@dataclassfield(default_factory) frozen=TruePydantic BaseModel__post_init__
Definition

The @dataclass decorator auto-generates __init__, __repr__, and __eq__ from class-level annotations — eliminating boilerplate for data-holding objects.

Why use it

Agent configs, tool definitions, and structured outputs need clean, readable classes. Dataclasses give you typed, documented, printable objects in half the lines of a regular class.

from dataclasses import dataclass, field
from typing import Optional

@dataclass
class AgentConfig:
    model:         str            = "claude-sonnet-4-20250514"
    max_tokens:    int            = 1024
    temperature:   float          = 0.7
    tools:         list[str]      = field(default_factory=list)  # ← NEVER use [] as default!
    system_prompt: Optional[str]  = None

    def __post_init__(self):           # runs after __init__ for validation
        if self.temperature < 0 or self.temperature > 2:
            raise ValueError("temperature must be 0–2")

@dataclass(frozen=True)             # immutable — safe as dict key / hashable
class ToolCall:
    name:      str
    arguments: tuple               # frozen requires all fields be immutable
Pydantic BaseModel = dataclass + runtime validation. Use it when parsing data from external sources (LLM JSON output, API responses). Use plain @dataclass for internal config you fully control.
How this connects to AI Agents

Every agent config, tool definition, and structured LLM response is a dataclass or Pydantic model. When you use structured output mode (asking the LLM to return JSON matching a schema), you define a Pydantic model and the response parses directly into it — typed, validated, documented. FastAPI uses Pydantic for request/response schemas. LangChain uses it for tool argument definitions. Dataclasses are also the backbone of message history serialisation in checkpointed agents.

Error Handling
try/except/else/finally · custom exceptions · re-raise · logging · contextlib.suppress
try / exceptraise custom Exceptionfinally logging.exceptioncontextlib.suppress
Definition

Error handling anticipates failures and responds gracefully. Python uses try/except/else/finally blocks. Custom exception classes form hierarchies that let callers handle errors at the right granularity.

Why use it

Agents fail constantly in production: rate limits, malformed LLM JSON, tool timeouts, context overflow. Without structured error handling the whole agent crashes on the first hiccup.

class AgentError(Exception): ...
class RateLimitError(AgentError):
    def __init__(self, retry_after: int):
        self.retry_after = retry_after
        super().__init__(f"Rate limited – retry after {retry_after}s")

async def safe_llm_call(prompt: str) -> str:
    try:
        return await call_llm(prompt)
    except RateLimitError as e:
        await asyncio.sleep(e.retry_after)
        return await safe_llm_call(prompt)       # retry once
    except ContextOverflowError:
        truncate_memory()                          # shed oldest messages
        return await safe_llm_call(prompt)
    except AgentError:
        logging.exception("unhandled agent error") # logs full traceback
        raise                                      # re-raise: don't swallow
    finally:
        logging.debug("LLM call attempt finished") # always runs
Rule: every except block should either recover (retry, truncate, fallback) or re-raise with added context. Silent swallowing of exceptions is the #1 cause of mysterious agent failures.
How this connects to AI Agents

Production agents fail in many ways simultaneously. Custom exception hierarchies let you handle each failure class differently: retry rate limits, truncate on context overflow, log and skip on tool errors. You'll wrap every LLM API call, tool execution, and vector DB query in structured try/except. Agents that don't handle errors gracefully appear broken to users after the very first rate limit — which happens constantly at scale.

Iterators & Generators
yield · yield from · generator expressions · async generators · itertools · __iter__ / __next__
yieldyield from async foritertools __iter__ / __next__
Definition

A generator is a function that produces values lazily using yield. It pauses execution between yields — computing one value at a time without building the whole result in memory.

Why use it

LLM responses stream token-by-token. Users must see output immediately — not after the full response. Async generators model this perfectly: yield each token as it arrives from the API stream.

# ── sync generator: chunk docs for RAG embedding ─────────────
def chunk_docs(docs: list[str], size: int = 512):
    for doc in docs:
        for i in range(0, len(doc), size):
            yield doc[i:i + size]    # no full list in memory

# ── async generator: stream tokens from Anthropic API ────────
async def stream_llm(prompt: str):
    async with client.messages.stream(
        model="claude-sonnet-4-20250514",
        messages=[{"role":"user", "content":prompt}],
        max_tokens=1024
    ) as stream:
        async for text in stream.text_stream:
            yield text               # push each token to caller immediately

# ── consuming the async generator in FastAPI (SSE) ───────────
async for token in stream_llm("Summarise this doc"):
    print(token, end="", flush=True)
How this connects to AI Agents

Streaming is the default UX for LLM apps — users see tokens appear in real time. The Anthropic SDK exposes streaming directly as an async generator. For RAG pipelines, generators let you chunk, embed, and index millions of documents without memory overflow. itertools.batched / islice efficiently batch documents for embedding API calls. Generators also power tool-result streaming in multi-step agents, forwarding partial results before the full chain is complete.

Context Managers
with · __enter__ / __exit__ · @contextmanager · asynccontextmanager · resource cleanup
with__enter__ / __exit__ @contextmanagerasync with contextlib.suppress
Definition

A context manager wraps a block with guaranteed setup + teardown. __enter__ runs on entry; __exit__ runs on exit — even if an exception was raised inside the block.

Why use it

Agents open resources constantly: HTTP sessions, DB connections, file handles, code sandboxes. Context managers guarantee these close cleanly — no leaked connections, no orphaned processes.

from contextlib import asynccontextmanager
import time, logging

# ── custom: time every LLM span and log it ───────────────────
@asynccontextmanager
async def timed_span(name: str):
    t0 = time.perf_counter()
    logging.info(f"[{name}] start")
    try:
        yield                             # body executes here
    finally:                              # always runs — even on error
        ms = (time.perf_counter() - t0) * 1000
        logging.info(f"[{name}] {ms:.0f}ms")

# usage
async with timed_span("search_tool"):
    result = await search(query)          # latency always logged

# ── aiohttp session: connection pool auto-closed ─────────────
async with httpx.AsyncClient() as client:
    resp = await client.get(url)          # socket closed even on error
How this connects to AI Agents

The Anthropic SDK's client.messages.stream() is an async context manager. Database connection pools, vector DB sessions, and code sandbox environments all use them. You'll build custom ones for tracing every LLM span (start time, end time, tokens), managing DB transactions, and wrapping code execution sandboxes that must be torn down after each tool call. Without this, leaked connections silently degrade agent performance over time.

Modules & Packaging
import system · __init__.py · pyproject.toml · virtual environments · relative imports · __all__
importfrom x import y pyproject.toml__init__.py venv / pip__all__
Definition

A module is any .py file. A package is a directory with __init__.py. Python resolves import names to files, executes them once, and caches them in sys.modules.

Why structure it

A real agent is a software system, not a script. Proper packaging separates concerns (tools / memory / orchestration), makes code testable, and ensures identical environments between laptop and production container.

Always isolate with a virtual environment: python -m venv .venv → source .venv/bin/activate. Never install globally — dependency version conflicts between projects silently break agents.
How this connects to AI Agents

A production agent is packaged properly so it can be installed in Docker with pip install -e ., tested with pytest, and deployed with all its dependencies locked. Circular imports are a common bug in agent code (tools importing agents that import tools) — understanding Python's import resolution helps you structure the code to avoid them. __all__ defines the clean API surface teammates and framework integrations rely on. pyproject.toml pins exact dependency versions so the production container runs identically to your laptop.
