01

Why Does Docker Even Exist?

Before a single command, you need to feel the pain that Docker was built to solve. Otherwise none of it will feel meaningful.

🎂 Analogy that makes it click

Imagine you bake a perfect cake at home. You write down the recipe and send it to a friend. But their oven is different, their flour brand is different, and they're at a different altitude — the cake comes out wrong. Docker is like shipping the actual baked cake in a sealed, perfect box instead of just the recipe. Your friend opens the box and eats the exact same cake. No re-baking needed, no variables.

✅ Problems Docker solves

• "Works on my machine" — gone forever
• Conflicting Python/library versions
• Hours of manual server setup
• Different dev vs production environments
• Painful onboarding for new teammates

🚫 What Docker is NOT

• Not a virtual machine (much lighter)
• Not a cloud platform (it works everywhere)
• Not only for servers (great for local dev too)
• Not only for big companies
• Not complicated once the mental model clicks

02

The Mental Model — 3 Things to Understand

Everything in Docker flows from just three concepts. Get these right and every command makes sense automatically.

🎬 Movie analogy — the one that sticks

The Dockerfile is the movie script (instructions for what should happen). The Image is the finished movie on a Blu-ray disc — complete, sealed, can't be edited, can be copied a thousand times. The Container is the movie playing on your TV right now — that's the actual live running process. You can play the same Blu-ray on many TVs simultaneously — that's running many containers from one image.

📦 Image — Static

  • Read-only, never changes once built
  • Stored on disk like a file
  • Can be shared and copied anywhere
  • Like a class definition in Python
  • Exists with no container running from it

📫 Container — Live

  • A running, alive process
  • Has its own isolated filesystem
  • Has its own isolated network
  • Like an object instance in Python
  • Can be started, stopped, and deleted

04

Images — The Sealed Box

An image is a complete, portable package: operating system slice + your language runtime + your libraries + your code — all frozen together, ready to run anywhere.

Where do images come from?

1. Docker Hub

Official public registry. Pre-built images for everything: python:3.11, postgres:16, ubuntu:22.04. You just docker pull them — instantly.

2. Build yourself

Write a Dockerfile, run docker build. Creates a custom image with your app code and dependencies baked in.

3. Private Registry

Your company's own hub (AWS ECR, Google GCR, GitHub GHCR). Same idea but private — only your team can access.

Image commands

Image commandsbash
# Download an image without running it
docker pull python:3.11-slim

# See all images stored on your machine
docker images

# Remove an image you no longer need
docker rmi python:3.11-slim

# Check an image's history (layers it was built from)
docker image history python:3.11-slim
🏷️
What is a TAG? Tags are version labels. In python:3.11-slim — "python" is the repository name, "3.11-slim" is the tag. latest is the default tag if you don't specify. Always pin to a specific tag in production — latest can change unexpectedly and break your code.

How layers work (simply explained)

Think of an image as a stack of transparent sheets. Each Dockerfile instruction adds one sheet. When you change your app code and rebuild, Docker reuses all the unchanged layers from cache — only rebuilds from the changed layer down. This turns 3-minute rebuilds into 3-second rebuilds.

05

Containers — The Running Box

A container is a live, isolated process. Think of it as a lightweight mini-computer running inside your computer — completely self-contained.

🗂 Own filesystem

Files inside the container are completely separate from your machine's files. The container can't see your Documents folder. Your machine can't see container's /app folder — unless you explicitly connect them with a volume.

🌐 Own network

The container gets its own private IP. If your app runs on port 5000 inside the container, you can NOT reach it from your browser unless you explicitly map the port using -p. Isolation by default.

⚡ Extremely lightweight

Not a full OS. Shares the host's Linux kernel. Starts in under 1 second. Uses 10–50 MB RAM for a simple app. Compare: a virtual machine needs 1–2 GB RAM and 30 seconds just to boot.

⚠️ Data warning

By default, when a container is deleted, ALL data written inside it is gone forever — files, database rows, everything. To keep data, you need volumes (covered next). This is one of the biggest beginner surprises.

Core container commands

Container commandsbash
# List running containers
docker ps

# List ALL containers including stopped ones
docker ps -a

# Stop a running container (graceful shutdown)
docker stop <container-id-or-name>

# Start a stopped container again
docker start <name>

# Delete a stopped container
docker rm <name>

# Shell inside a running container (for debugging)
docker exec -it <name> bash

# See live output / logs from a container
docker logs -f <name>
06

The Dockerfile — Your Recipe

A Dockerfile is just a plain text file (no extension) with step-by-step instructions. Each line is one building block of your image.

The most common Dockerfile for Python

Dockerfiledockerfile
# 1. Start from a base image — Python already installed inside
FROM python:3.11-slim

# 2. Set working directory inside container (create if not exist)
WORKDIR /app

# 3. Copy ONLY requirements first (cache trick — see below!)
COPY requirements.txt .

# 4. Install dependencies — this layer gets cached
RUN pip install -r requirements.txt

# 5. Copy rest of your code (changes most often — so it goes last)
COPY . .

# 6. What command runs when container starts
CMD ["python", "app.py"]
InstructionPlain English Meaning
FROM python:3.11-slim"Start from an image that already has Python 3.11 installed. Use the slim (smaller) variant."
WORKDIR /app"From now on, all commands run inside the /app folder inside the container. Create it if it doesn't exist."
COPY requirements.txt ."Copy this file from my machine into the container's current folder (/app)."
RUN pip install -r requirements.txt"Execute this shell command while building the image. Install Python packages."
COPY . ."Copy everything in my current folder into the container's /app folder."
CMD ["python", "app.py"]"When someone starts a container from this image, run this command automatically."

Build & run it

Build image, then run containerbash
# Build: reads Dockerfile, creates image named my-app with tag 1.0
# The "." at the end = "use current folder as build context"
docker build -t my-app:1.0 .

# Verify the image was created
docker images

# Run it as a container
docker run -d -p 5000:5000 --name my-flask my-app:1.0
07

Port Mapping — Opening the Door

This is the most confusing topic for beginners. Understand this and it never trips you up again.

🚪 Analogy — apartment building

Imagine the container is an apartment on the 5th floor. Port 5000 inside the container is the apartment's internal room number. From outside the building (your browser), you can't just knock on room 5000 — you need the building's main entrance. Port mapping is like telling the doorman: "Anyone who comes to the building door asking for port 8080 — take them to apartment 5000 on the 5th floor."

Port mapping examplesbash
# Map host 5000 → container 5000 (same port)
docker run -p 5000:5000 my-app:1.0

# Map host 8080 → container 5000 (different ports)
docker run -p 8080:5000 my-app:1.0
# Now visit localhost:8080 in browser → hits container port 5000

# Run in detached mode (background) + give it a name
docker run -d -p 5000:5000 --name my-server my-app:1.0
⚠️
No port mapping = completely unreachable from outside. If you forget -p, your app runs fine inside the container but you cannot reach it. The browser will say "connection refused". Just add the -p flag.
08

Volumes — Keeping Your Data

By default containers are ephemeral — delete the container, all data inside it vanishes. Volumes solve this.

🏨 Hotel room analogy

A container without volumes is like a hotel room — everything resets when you check out. A bind mount is like bringing your own laptop to the hotel — your files stay on your laptop no matter what. A named volume is like renting a storage unit near the hotel — you deposit things, they stay there safely even after you check out, and you can pick them up when you return.

Bind Mount — for development

Links a specific folder on your actual computer into the container. When you edit a file on your machine, the change is instantly visible inside the container. Perfect for live-reload dev workflows.

Syntax
docker run -v $(pwd):/app my-app:1.0
# $(pwd) = your current folder
# /app = folder inside container

Named Volume — for persistence

Docker manages the storage for you. Survives container deletion. Perfect for databases, model weights, anything that must persist across container restarts.

Syntax
docker volume create my-data
docker run -v my-data:/app/data my-app:1.0
docker volume ls      # list volumes
TypeSyntaxUse caseSurvives container rm?
Bind Mount-v /your/path:/ctr/pathDev live-reload, local datasetsYes — it's your own files
Named Volume-v vol-name:/ctr/pathDB data, model weightsYes — Docker keeps it
tmpfs--tmpfs /tmpSecrets, temp scratchNo — RAM only, gone on exit
09

Networks — Containers Talking to Each Other

By default, containers are islands — totally isolated. When you need two containers to communicate (like an app and its database), you need a Docker network.

📡 Office Wi-Fi analogy

A Docker network is like a private office Wi-Fi. Any device (container) you connect to that Wi-Fi can find and talk to any other connected device — by name, not IP address. Devices on different Wi-Fi networks can't reach each other. The key magic: Docker DNS automatically resolves container names to their internal IPs. So if your database container is named "my-db", your app container can connect to http://my-db:5432 without ever knowing the actual IP.

Connect two containers on same networkbash
# Step 1: Create a shared network
docker network create my-net

# Step 2: Run the database on that network, give it a name
docker run -d \
  --name my-db \
  --network my-net \
  -e POSTGRES_PASSWORD=secret \
  postgres:16

# Step 3: Run your app on the same network
docker run -d \
  --name my-app \
  --network my-net \
  -p 8000:8000 \
  my-flask-app:1.0

# Inside my-app, connect to database using name as hostname:
# "postgresql://user:secret@my-db:5432/mydb"
# Docker DNS resolves "my-db" to its IP automatically ✓
🔑
The golden rule: Never hardcode container IPs like 172.19.0.3 in your code. Container IPs can change on restart. Always use the container's name as the hostname — it's stable and Docker resolves it automatically.
10

Docker Compose — One File, Everything

Once you have 2+ containers, managing them with individual docker run commands gets messy fast. Docker Compose is the solution.

😩 Without Compose — 4 commands to memorize

docker network create my-net
docker run -d --name db \
  --network my-net \
  -e POSTGRES_PASSWORD=s3cr3t \
  postgres:16
docker run -d --name redis \
  --network my-net redis:7
docker run -d --name api \
  --network my-net -p 8000:8000 \
  my-api:1.0

😊 With Compose — 1 command forever

# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: s3cr3t
  redis:
    image: redis:7
  api:
    build: .
    ports: ["8000:8000"]

# Then just:
docker compose up -d

The 5 Compose commands you need

CommandWhat it does
docker compose up -dBuild if needed, start all services in background. Creates network automatically.
docker compose up --buildForce-rebuild images before starting. Use after code changes.
docker compose downStop + remove containers + network. Safe — volumes are preserved.
docker compose logs -fStream logs from all services. Add service name to filter: logs -f api.
docker compose exec api bashShell into a running service by name.
11

Registries — Sharing Your Image

Your built image only exists on your machine. To run it on a server, or share it with a teammate, you push it to a registry — essentially GitHub but for Docker images.

📦 Courier service analogy

Your built image is a package sitting in your room. Docker Hub is the courier depot. You drop off the package (docker push). Anyone with the tracking number (image name + tag) can pick it up from any depot branch anywhere in the world (docker pull). Your production server pulls the same identical package you tested on your laptop.

Full push/pull workflowbash
# 1. Login to Docker Hub
docker login
# Enter your username + password

# 2. Tag the image with your username (required format)
docker tag my-app:1.0 your-username/my-app:1.0

# 3. Push to Docker Hub
docker push your-username/my-app:1.0

# 4. On any other machine — pull and run it
docker pull your-username/my-app:1.0
docker run -d -p 5000:5000 your-username/my-app:1.0
RegistryBy whomBest for
Docker HubDocker Inc.Public images, personal projects, free tier
ECRAmazon (AWS)Production on AWS, integrates with ECS/EKS
GCR / GARGoogle CloudProduction on GCP, integrates with Cloud Run/GKE
GHCRGitHubOpen source projects, CI/CD with GitHub Actions

The Story — Arjun's Journey with Docker

Every concept you've read above — Images, Containers, Dockerfiles, Volumes, Networks, Compose, Registries — plays a real role in the story below. Read it like a novel. The command names and concept names appear in orange as they happen naturally in the story.

📍 Scene 1 · The Problem

Monday morning. Arjun is furious.

Arjun is a junior AI engineer. He spent three days building a Python Flask app that classifies images using a PyTorch model. It works perfectly on his Mac. He zips the code and sends it to his senior, Priya, who is on Ubuntu.

Ten minutes later, Priya calls: "Arjun, it's crashing immediately. ModuleNotFoundError: Flask. Also you're on Python 3.11 but our server runs 3.7."

This is the classic "it works on my machine" problem. Different Python versions. Missing libraries. Different operating systems. Arjun's code is correct — but the environment around it is different everywhere.

Priya says: "You need to learn Docker. You don't send the code — you send the whole environment with the code inside it."

Arjun opens his terminal and types his first Docker command ever:

docker --version → Docker version 26.0.0 → Good, it's installed.

Then he runs: docker run hello-world — and sees the famous "Hello from Docker!" message. Docker pulled a tiny image from the internet called hello-world, ran it as a container, printed the message, and exited — all in 3 seconds. Arjun starts to feel it.

📍 Scene 2 · Writing the Recipe

Arjun writes his first Dockerfile.

Priya explains: "Think of a Dockerfile as a cooking recipe. You write instructions: start with these ingredients, do these steps, and the result is a sealed box containing everything your app needs."

Arjun creates a file called Dockerfile in his project folder — no extension, just that name. He writes:

FROM python:3.11-slim — "Start from a base image that already has Python 3.11 inside. I don't need to install Python myself."

WORKDIR /app — "Set the working folder inside the container to /app. All my files will live here."

COPY requirements.txt . — "Copy my requirements file into the container."

RUN pip install -r requirements.txt — "Install Flask and PyTorch inside the container while building."

COPY . . — "Now copy the rest of my code."

CMD ["python", "app.py"] — "When someone starts a container from this, run app.py."

Priya tells him something critical about the order: "Notice you copied requirements.txt and ran pip install BEFORE copying the rest of your code. That's intentional."

She explains: Docker caches each instruction as a layer. If you change app.py and rebuild, Docker reuses the cached pip install layer — it doesn't reinstall Flask again. That turns a 3-minute rebuild into a 3-second one. But if you copy all your code first and then run pip install — any code change invalidates the pip cache and you wait 3 minutes every single time.

The golden rule: put the slow, rarely-changing stuff early. Put your frequently changing code at the bottom.
📍 Scene 3 · Building the Image

The recipe becomes the sealed box.

Arjun runs: docker build -t my-classifier:1.0 .

The -t flag gives the image a name and version tag. The dot at the end means "use the current folder as the build context — Docker can only see files here." He watches as Docker executes each instruction, one by one, like following a recipe step by step.

Downloading python:3.11-slim base... Installing Flask... Installing PyTorch... Copying code...

After 2 minutes, it finishes. He runs docker images and sees:

REPOSITORY       TAG   IMAGE ID       SIZE
my-classifier   1.0   a1b2c3d4e5f6   1.2GB

This is the image — a frozen, read-only snapshot. It contains Python 3.11, Flask, PyTorch, and Arjun's entire code — all baked in. He can now send this image to Priya. It will run identically on her Ubuntu machine because the environment is fully self-contained inside the image.

He changes one line in app.py and rebuilds. This time: 4 seconds. The pip install layer was cached. Arjun literally says "oh wow" out loud.

📍 Scene 4 · The Container Can't Be Reached

Arjun runs the image. The app doesn't respond.

He runs: docker run my-classifier:1.0

The terminal shows: "Flask running on 0.0.0.0:5000". He opens a browser and visits localhost:5000. Connection refused.

Arjun stares at his screen. The app IS running. Why can't he reach it?

Priya explains with the apartment analogy: "A container is an isolated box. It has its own private network. Port 5000 is open INSIDE the container — but nothing connects it to your machine's port 5000. You need to explicitly punch a hole between outside and inside."

That hole is called port mapping. The -p flag.

He runs: docker run -d -p 5000:5000 --name classifier my-classifier:1.0

The -d runs it in the background (detached). The -p 5000:5000 maps his machine's port 5000 to the container's port 5000. The --name gives it a friendly name instead of a random ID.

He visits localhost:5000. The app responds. He checks the running container with docker ps — sees its name, image, status, and port mapping all listed clearly. He checks logs with docker logs -f classifier — sees real-time output streaming from inside the container. He is in control.

📍 Scene 5 · The Edit-Rebuild Loop is Painful

Every code change requires a full rebuild. Arjun loses 10 minutes per hour.

He changes the confidence threshold in app.py. Stops the container. Rebuilds the image. Starts a new container. Tests it. Repeat. Even with caching, it's 8–10 seconds of friction every single time, plus remembering to stop and restart.

Priya teaches him about bind mounts.

"Instead of baking your code into the image during development, just link your code folder directly into the container. The container reads your files live, in real time. When you save a file, the container immediately sees the change — without any rebuild."

He runs: docker run -d -p 5000:5000 -v $(pwd):/app my-classifier:1.0

-v $(pwd):/app is the bind mount. $(pwd) is his current folder on his Mac. /app is the folder inside the container. They are now the same folder — a two-way live mirror.

He edits app.py, saves it. Flask detects the change and reloads automatically (because he added --reload to the Flask command). He refreshes the browser — the change is there. Zero rebuild time. He can iterate at full speed.

"This is the bind mount," Priya says. "Your code lives on your machine. The container just reads it through a portal."

📍 Scene 6 · Two Services Need to Talk

Arjun's app needs a database. The containers can't find each other.

The app needs to store prediction results in a PostgreSQL database. Arjun runs a Postgres container: docker run -d --name my-db -e POSTGRES_PASSWORD=secret postgres:16

He updates app.py to connect to the database at localhost:5432. The app crashes: connection refused to localhost:5432.

The problem: each container has its own isolated network. "localhost" inside the app container means the app container itself — not Priya's machine, not the database container. The two containers are on separate islands with no bridge between them.

Solution: Docker networks.

docker network create app-net — creates a private shared network

Run both containers on this network:
docker run -d --name my-db --network app-net -e POSTGRES_PASSWORD=secret postgres:16
docker run -d --name classifier --network app-net -p 5000:5000 my-classifier:1.0

Now here's the magic: Arjun changes the database connection string in his code from localhost:5432 to my-db:5432. The container's NAME becomes its hostname on the network. Docker's built-in DNS resolves "my-db" to the database container's internal IP automatically.

The app starts. It connects to the database. Predictions are stored. Arjun runs docker network inspect app-net and sees both containers listed with their internal IPs — 172.20.0.2 and 172.20.0.3. But his code never needs to know these IPs. It just says "my-db" and Docker handles the rest.

The rule: Never hardcode container IPs. Use container names as hostnames. They're stable and DNS-resolved automatically.
📍 Scene 7 · Database Data Vanishes on Restart

Arjun deletes the database container. All his test data is gone.

He runs docker rm -f my-db to restart fresh. When he creates a new Postgres container, all the stored predictions are gone. Empty database.

This is the default container behavior: ephemeral. When a container dies, everything written inside it dies with it. The filesystem is temporary.

For the database, Arjun needs a named volume.

docker volume create pg-data

docker run -d --name my-db --network app-net -v pg-data:/var/lib/postgresql/data -e POSTGRES_PASSWORD=secret postgres:16

Now the Postgres data directory is stored in the pg-data named volume — managed by Docker, living outside any container. He deletes the container, creates a new one with the same volume, and the data is still there. The volume outlives any individual container.

"Named volumes are for data that must survive," Priya says. "Bind mounts are for your code during development. tmpfs is for secrets that should never touch disk."

📍 Scene 8 · The Startup Script is a Nightmare

Arjun writes a 6-step bash script to start his stack. A new teammate breaks it in 2 minutes.

His stack now has three containers: the classifier app, the database, and a Redis cache. Each needs the right flags, in the right order, on the right network. He writes a startup script. His new teammate Rohan runs it on Windows — different path syntax, different shell. It breaks.

Priya introduces Docker Compose.

"Docker Compose lets you describe your entire application stack in a single YAML file. One command starts everything, in the right order, on a shared network, with all the right flags — automatically. And it works identically on Mac, Linux, and Windows."

Arjun creates docker-compose.yml:

Every container becomes a service. The service name becomes its hostname. The network is created automatically. Build instructions, port mappings, volumes, environment variables — all written once, declaratively.

Now Rohan runs a single command: docker compose up -d. All three containers start in 10 seconds. Rohan immediately gets a working environment without understanding a single Docker flag. Arjun runs docker compose logs -f classifier to stream just the classifier service logs. He runs docker compose down at the end of the day — everything stops, network is removed, volumes are safe.

The entire team is now running the identical stack. The "it works on my machine" era is over for Arjun's team.

📍 Scene 9 · Deploying to the Cloud

The image on Arjun's laptop needs to reach the production server.

The app is ready. The production server is an AWS EC2 instance. Arjun can't run docker compose up on his laptop and have it deploy to AWS. The image exists only on his machine.

He needs to push it to a registry.

Priya explains: "A registry is like GitHub but for Docker images. You push your image there. The server pulls from there. AWS ECR, Google GCR, Docker Hub — all registries. They're neutral storage. Your laptop pushes, the server pulls. The image is identical."

docker login — authenticate to Docker Hub
docker tag my-classifier:1.0 arjun/classifier:1.0 — give the image the right name format
docker push arjun/classifier:1.0 — upload to Docker Hub

On the production server:
docker pull arjun/classifier:1.0
docker run -d -p 80:5000 arjun/classifier:1.0

The production server downloads the exact same image — same Python version, same Flask version, same model weights path, same code. Not "a similar version" — the identical binary artifact, guaranteed by the image SHA256 hash. The application runs the first time, without any setup, without any install scripts, without any "it worked on my machine" drama.

Priya smiles at the commit message Arjun writes that evening: "Dockerized. Will never send raw code again."

🏁 Epilogue · Six Months Later

Arjun is now the one teaching Docker.

The AI team has grown. When a new engineer, Kavya, joins, her onboarding is: "Clone the repo. Run docker compose up. You're ready."

Every concept Arjun learned has a permanent home in his mental model:

📝 Dockerfile — the recipe he writes once
📦 Image — the sealed box it produces
📫 Container — the live, running instance of that box
🚪 Port mapping — the tunnel from the outside world into the box
💾 Bind mount — the portal that keeps dev files live
🔒 Named volume — the safe where persistent data lives
🌐 Network — the private Wi-Fi connecting all the boxes
🎼 Compose — the conductor that starts the whole orchestra with one command
☁️ Registry — the depot where images travel from his laptop to the world

"Docker isn't magic," Arjun tells Kavya. "It's just a very elegant system of boxes, labels, tunnels, and shared folders. Once you see it, you can't unsee it."

Readiness Checklist

Before opening the Advanced AI Engineer notes, go through this list. Each item should be a confident yes — from hands-on practice, not just reading.

Concepts — can you explain these without looking?

  • ☐I can explain the "it works on my machine" problem and why Docker solves it
  • ☐I can explain the difference between an Image and a Container using an analogy
  • ☐I understand that a container is isolated — own filesystem, own network, no access to host by default
  • ☐I can explain what each Dockerfile instruction does: FROM, WORKDIR, COPY, RUN, CMD
  • ☐I understand why you copy requirements.txt and pip install BEFORE copying your code (cache trick)
  • ☐I can explain port mapping — what the left number and right number mean in -p 8080:5000
  • ☐I know the difference between a bind mount and a named volume and when to use each
  • ☐I understand how containers on the same network find each other by name (Docker DNS)
  • ☐I understand what Docker Compose solves that raw docker run commands don't
  • ☐I know what a registry is — push to share, pull to deploy

  • ☐Used docker ps, docker logs -f, docker stop, docker rm
  • ☐Used a bind mount (-v $(pwd):/app) and edited a file — saw the change reflect inside the container live
  • ☐Wrote a docker-compose.yml, ran docker compose up -d, then docker compose down
